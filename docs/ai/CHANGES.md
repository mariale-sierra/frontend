## Changelog

### 2026-07-15
- **Changed (Fase 2 completion — API centralization + client security):** consolidated the two enrolled-challenges functions (`challenge.service.getUserEnrolledChallenges` vs `user.service.getMyChallenges`) into one canonical `getMyChallenges` (`services/user/user.service.ts`), matching the backend's real `{active, completed, left}` response shape; migrated its only other caller (`hooks/useMetricsScreen.ts`, now filters to `status === 'active'`). Applied the Fase 1 backend contract deltas: dropped `userId` from `CreateWorkoutLogRequest`/`createWorkoutLog` and `createdByUserId` from `CreateRoutineRequest`/`createRoutine` (both now come from the JWT server-side). Moved the API base URL out of `services/api.ts` into `app.config.js`'s `extra.apiUrl` (override via `EXPO_PUBLIC_API_URL`), still defaulting to `http://20.63.84.1:3000` over plain HTTP — HTTPS is a pending infra dependency, not fixed here. Installed `expo-secure-store` and moved the JWT there (`utils/storage.ts`'s new `secureStorage`, used by `services/auth/token.service.ts`); userId/username stay in AsyncStorage. Existing logged-in users are logged out once after this change (SecureStore and AsyncStorage are different backing stores) — expected, not a bug. Translated `services/api.ts`'s response-interceptor toasts (401/403/404/500/network/unknown) to `i18n.t('common.errors.*')` instead of hardcoded Spanish.
- **Changed (Fase 6 — i18n sweep):** moved every hardcoded string in the plan's target list to `t()` — `(tabs)/index.tsx`, `(tabs)/add.tsx`, `(tabs)/search.tsx`, `challenge/[id]/index.tsx` (also fixed several `t(key, { defaultValue })` calls whose keys didn't actually exist in the resources — the `defaultValue` was silently doing all the work, meaning Spanish users saw English), `challenge/routine/select.tsx`, `exerciseMetricsEditor.tsx`, `exerciseNoteField.tsx`, `challengeRoutineList.tsx`, `(add)/plan-rest-days.tsx`, `(add)/camera.tsx`, `components/routine/builder/exerciseHeader.tsx` (Alert.alert literals), and the five stub screens (`recover-password.tsx`, `onboarding/{objectives,preferences,profile_type}.tsx`, `profile/[username].tsx`). Added ~35 new keys to both `en.ts`/`es.ts` (`common.errors.*`, `challenges.*`, `metrics.tableHeaders.*`, `routineCreate.*`, `routineSelect.*`, `home.*`, `addMenu.*`, `planRestDays.*`, `camera.*`, `challengeRoutineDay.*`, `placeholders.*`). Fixed the systematic missing-accent pattern across all of `es.ts` (`sesion→sesión`, `contrasena→contraseña`, `dia(s)→día(s)`, `categoria(s)→categoría(s)`, `ubicacion→ubicación`, `duracion→duración`, `descripcion→descripción`, `publico→público`, etc. — the full file, not just new keys). Verified en/es key parity (262 keys each, zero drift) with a one-off compiled-JS parity check (no test framework wired up yet, see `frontend/docs/ai/frontend/TESTING-GUIDE.md`).
- **Changed (Fase 3 — mock removal + refactor):** removed live-screen mocks: `(tabs)/index.tsx` no longer prepends `MOCK_BADGE_CHALLENGES` or falls back to `buildMockFeedPosts()` on feed-load failure (falls through to the existing empty-feed UI instead); `challenge/[id]/routine/[day].tsx` no longer has an `ENABLE_CHALLENGE_DETAIL_MOCK` fallback (flag removed entirely) and now renders a real empty state (`challengeRoutineDay.emptyTitle`/`.emptyMessage`) instead of `return null` when a day's routine data is incomplete — also fixed two `t()` calls in that file that were relying on `defaultValue` because `challengeRoutineDay.*` keys didn't exist yet. `components/challenge/progress/ChallengeActiveProgressScreen.tsx` no longer embeds `mockChallenge`/`getMockPublicPhotosForChallenge()`; its data-fetching moved into a new hook `hooks/useChallengeActiveProgress.ts`, making the component presentational (props from the hook in, JSX out). **Known backend gap surfaced by this change** (not fixed here — frontend can't fabricate data the API doesn't send): `GET /challenges/progress` has no participant roster and no per-day completion array, so `participants`/`completedWorkoutDays` are now honest empty defaults instead of fake names/"75 HARD" content; `startDate` is derived from `currentDay` + today's date (same technique already used in `plan-rest-days.tsx`), since the backend doesn't return an actual challenge start date either.
- **Deleted (dead mocks, confirmed unreferenced before removal):** `services/mocks/{exploreMock,activeMock,homeMock}.ts` and `components/ui/confirmationPopup.usage.tsx` (explicitly listed as dead in the restructuring plan), plus three more mock files that became dead as a *direct result* of the above changes and were removed in the same pass rather than left orphaned: `services/mocks/feedMock.ts` (only caller was the `(tabs)/index.tsx` fallback just removed), `services/mocks/challengeDetailMock.ts` (only caller was the `[day].tsx` mock fallback just removed), `services/mocks/publicChallengePhotos.ts` (only caller was `ChallengeActiveProgressScreen`'s mock fallback just removed). `services/mocks/` is now an empty directory.
- **Changed (`app/challenge/create.tsx` split, 773 → 538 lines):** extracted `CATEGORY_OPTIONS`/`LOCATION_OPTIONS`/`VISIBILITY_OPTIONS` (previously inline, marked `MOCK ONLY`) to `constants/challengeCreateOptions.ts`. Extracted the reusable option-picker UI (`SelectionPanel` + `OptionCard` + the generic `OptionSelectionPanel`) and the option-detail dialog (`OptionInfoModal`) out of `create.tsx` into new files under `components/challenge/create/`, registered in that folder's `index.ts` barrel. The per-step `renderStepContent()` switch was intentionally left in `create.tsx` — splitting each case into its own component would require threading ~15 `useCreateChallengeFlow()` values through new prop interfaces for uncertain benefit; not done.
- **Changed (unified challenge-create validation):** `hooks/useCreateChallengeFlow.ts` was independently re-declaring the same "is the form complete" rule twice — once as `missingConfigurationFields` (list of missing field labels) and again as `isFormComplete` (a separate `&&` boolean chain checking the identical seven conditions). `isFormComplete` now derives from `missingConfigurationFields.length === 0` instead of restating the rules. `services/adapters/createChallengePayloadAdapter.ts`'s `buildCreateChallengePayload` had a *third*, partial copy of the same validation (title/cycle/challenge-duration/missing-days checks, with hardcoded English error strings bypassing i18n) — removed; the adapter is now a pure payload transform (`BuildChallengePayloadParams → CreateChallengePayload`, no `BuildPayloadResult`/`ok` union), documented as intentionally unvalidated since `useCreateChallengeFlow`'s `missingConfigurationFields` already gates every caller. Removed the now-unreachable `challengeCreate.alerts.cannotBuildPayloadTitle` i18n key from both `en.ts`/`es.ts`.
- **Reason:** Fase 2/3/6 of the restructuring plan (`necesito-que-inspecciones-profundamente-sorted-lemur.md` §9), assigned to the Frontend Architecture agent.
- **Impact:** `frontend/docs/ai/frontend/API-CLIENT-GUIDE.md`, `COMPONENTS-GUIDE.md`, `FRONTEND-MAP.md`, `I18N-GUIDE.md`, and `frontend/docs/ai/CURRENT-STATE.md` updated in the same pass — see those files for the current-state detail this entry doesn't repeat.

### 2026-07-07
- **Changed:** adapted the `app-builder`/`app-builder-frontend` skills (copied in from a different project, "Klyro") to Havit's real stack, and bootstrapped this `docs/ai/` tree with real content for the first time.
- **Reason:** the copied skills assumed Next.js + shadcn/Radix + TanStack Query + react-hook-form/zod + an 8-language i18n setup and a multi-tenant business/branch context — none of which exist in this Expo/React Native codebase. Left as-is, they would have pushed future sessions toward inventing libraries/patterns that don't belong here.
- **Impact:** `docs/ai/frontend/FORMS-GUIDE.md`, `API-CLIENT-GUIDE.md`, `DESIGN-SYSTEM.md`, etc. now describe the actual (library-free forms, single Axios client, no query cache, two-language i18n) patterns.
